# Backend «Запары»

Backend FastAPI, PostgreSQL и Alembic с недельным кэшем расписания, аккаунтами и API планов. Нормализованные справочники и подключение существующих экранов планирования к сохранённым планам ещё не реализованы. Существующий frontend по-прежнему работает через свой прокси.

## Запуск в Docker

Команды выполняются из корня проекта. Скопируйте пример конфигурации и задайте свой пароль:

```bash
cp docker/backend.env.example docker/backend.env
```

Отредактируйте `docker/backend.env`: замените `ZAPARA_DB_PASSWORD`, при необходимости укажите имя базы и пользователя. Файл исключён из Git. Для локального сервера оставьте `ZAPARA_DB_HOST=postgres`.

Запустите локальный PostgreSQL и дождитесь готовности:

```bash
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml --profile local-db up -d --wait postgres
```

Выполните миграции и запустите API:

```bash
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml run --rm migrate
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml up -d api
```

API доступен на `http://127.0.0.1:8000`, документация — `/docs`. `/health/live` показывает, что приложение отвечает; `/health/ready` дополнительно проверяет соединение с БД и соответствие текущей версии миграций. До применения миграций или при недоступной БД readiness отвечает `503`.

Остановка контейнеров без удаления данных:

```bash
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml --profile local-db down
```

PostgreSQL хранит данные в отдельном Docker volume. Не используйте `down -v`, если данные нужно сохранить. При первом запуске PostgreSQL создаёт базу и пользователя из конфигурации; последующее изменение этих значений в файле не меняет уже созданные учётные данные или базу.

## Общий PostgreSQL

База `shared` может позже использоваться другими проектами. «Запара» хранит свои таблицы и `alembic_version` в схеме `zapara`, не затрагивая `public` и схемы других приложений. Каждая будущая миграция должна явно указывать схему `zapara`; автогенерацию нельзя запускать с удалением чужих объектов. Миграции создают историю Alembic и таблицы кэша в собственной схеме. Создание схемы выполняется при запуске Alembic до создания таблицы версий.

Для существующего сервера укажите `ZAPARA_DB_HOST`, порт, имя базы и учётную запись, доступную из контейнера API; сервис `postgres` в этом случае запускать не требуется. Учётной записи миграции нужны право подключения и право создать схему `zapara` либо доступ владельца к заранее созданной схеме. Если схема создана заранее, право `CREATE` на всю базу необязательно. Настройте отдельные роли и доступы для каждого проекта: схема сама по себе не ограничивает права пользователя PostgreSQL. Пример локального Compose использует начального пользователя PostgreSQL и предназначен для разработки; для общего сервера следует отдельно выдать минимально необходимые права и предусмотреть роль для миграций.

Миграции запускаются явно перед выпуском новой версии API, не выполняются автоматически каждым экземпляром приложения. Установка зависимостей и окружение приложения не создают и не удаляют базы или чужие схемы.

## Миграции

Внутри контейнера приложения команды Alembic запускаются из `/app`, например `alembic current` и `alembic upgrade head`. Для новой ревизии используйте `alembic revision -m "описание"` и явно указывайте `schema="zapara"` во всех операциях с таблицами. Ревизии хранятся в `backend/migrations/versions/`. Откат прикладных миграций нужно разрабатывать с учётом сохранности данных; базовая ревизия не удаляет схему.

## Кэш расписания

`GET /api/v1/schedule/{kind}/{external_id}?start=YYYY-MM-DD&finish=YYYY-MM-DD` принимает `person`, `group`, `auditorium`, `building` и числовой ID в пространстве соответствующей ручки ОмГТУ. Период ограничен 91 днём. Запрос разбивается на недельные окна; отсутствующие или устаревшие окна ставятся в очередь. Ответ содержит исходные записи, включая подгруппы, и состояние каждого окна (`fresh`, `stale`, `loading`, `unknown`). Пустой `events` при неполном покрытии не означает отсутствие занятий. Ручки пока не защищены авторизацией: порт Compose доступен только с локального компьютера.

Worker по умолчанию не запускается. После согласования допустимой частоты API задайте `ZAPARA_UPSTREAM_INTERVAL_SECONDS` в `docker/backend.env` (не менее 10 секунд) и запустите:

```bash
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml --profile worker up -d worker
```

Общий лимит и блокировка действуют для всех worker, использующих одну БД. Запросы выполняются последовательно; ошибки и HTTP 429 задерживают повтор, `Retry-After` учитывается. Ответ с ошибкой, слишком большой или некорректный не заменяет последний успешный ответ. Запрошенные окна текущей и четырёх следующих недель обновляются после истечения 24 часов в течение 30 дней после последнего обращения. При наличии настроенной кафедры и актуального справочника преподавателей worker создаёт окна по `person` ID сотрудников кафедры на текущую и следующие четыре недели. Объекты без корректного `person` ID не планируются; полное ежедневное обновление не гарантируется, если очередь не укладывается в установленный лимит. Планирование остальных дат остаётся по запросу.

## Справочники

`GET /api/v1/dictionaries/{kind}` принимает `groups`, `lecturers`, `buildings`, `auditoriums`; для аудиторий дополнительно допускается `?buildingOid=18`. Справочник и его область кэшируются отдельно, а состояние (`loading`, `fresh`, `stale`, `unknown`) показывает доступность данных. Запрос ставит отсутствующий или устаревший справочник в ту же очередь и под тот же общий лимит, что и расписания. При пустом ответе справочника полнота не подтверждена: возвращается `unknown` или предыдущие данные со статусом `stale`, повтор выполняется с задержкой. В справочнике преподавателей хранятся только поля для расписания и сопоставления, без email и идентификаторов кадровой системы. Связь преподавателя с кафедрой и нормализованные справочники ещё не реализованы.

### Если контейнер не выходит в сеть

На Linux, если Docker bridge не может подключиться к API вуза, можно применить дополнительный Compose-файл `docker/compose.backend.host-network.yaml`. Он запускает **только worker** в сети хоста и открывает локальный PostgreSQL на `127.0.0.1:15432`; остальные сервисы остаются в обычной Docker-сети. При необходимости задайте `ZAPARA_HOST_DB_PORT` в `docker/backend.env`. Перед использованием убедитесь, что порт свободен и worker включён в конфигурации.

Используйте оба файла для всех соответствующих команд этого запуска, например:

```bash
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml -f docker/compose.backend.host-network.yaml --profile local-db up -d --wait postgres
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml -f docker/compose.backend.host-network.yaml run --rm migrate
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml -f docker/compose.backend.host-network.yaml --profile worker up -d api worker
```

Этот вариант предназначен для локального PostgreSQL. Для внешнего сервера настройте адрес и права подключения отдельно. Применение сетевого режима хоста зависит от платформы Docker; вариант по умолчанию предпочтителен, когда bridge-сеть работает.

## Аккаунты и планы

После применения миграций первый системный администратор создаётся один раз оператором:

```bash
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml run --rm api \
  python -m app.bootstrap --email admin@example.com --name "Имя администратора" \
  --department "Прикладная математика и фундаментальная информатика" --chair-oid 46
```

Команда выводит одноразовый токен установки пароля, действительный 24 часа. Для активации можно открыть сайт с фрагментом `#activation=ТОКЕН` или передать токен в `POST /api/v1/auth/activate`. Токен и пароль нельзя передавать через журналы или общедоступные каналы. Повторный bootstrap при существующем системном администраторе отклоняется.

Запуск сайта вместе с backend после сборки `frontend/dist`:

```bash
docker build -f docker/Dockerfile.build --target export --output type=local,dest=frontend/dist frontend
docker compose --env-file docker/backend.env -f docker/compose.backend.yaml --profile web up -d api web
```

Сайт доступен на `http://127.0.0.1:8081`; кнопка входа открывает аккаунт и управление сотрудниками. Без входа доступны главная, расписание групп и расписание преподавателей; разделы планирования появляются после входа с правами сотрудника или администратора. Сессия хранится в пределах текущей вкладки и проверяется сервером при восстановлении. Ссылка активации передаётся вручную, без email-сервера. При разработке Vite проксирует `/backend-api` на локальный backend. У nginx для этих маршрутов используется сервис `api` в сети Compose; для другого способа развёртывания обратный прокси нужно настроить отдельно.

API выдаёт ограниченную по времени непрозрачную bearer-сессию; в БД хранится её хеш. Расписание и справочники защищены этой сессией. Доступны операции создания планов и выбранных пар, назначения доступа сотрудникам, выбора и подтверждения замен, подтверждения пар, архивации и просмотра уведомлений. При конфликте сервер возвращает `409` с перечнем и хешем состояния; повторное подтверждение требует этот хеш и причину. Известный конфликт с расписанием может подтвердить только сотрудник с отдельным правом или администратор кафедры.

**Текущие ограничения:** существующие экраны консультаций, пересдач, встреч и замен ещё не подключены к этим API и сохраняют выбор прежним способом; полноценные восстановление архивного плана и идемпотентность повторов команд ещё не реализованы. Изменение привязки преподавателя доступно через API администратора. Подключение пользовательских экранов и эти операции необходимы до перехода на backend как основной способ работы.
